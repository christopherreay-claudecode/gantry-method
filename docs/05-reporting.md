# 05 — Reporting: corporate documents derived from the graph

Who this is for: any agent or person producing a report (status report,
board pack, distributor brief, patent update) for a client that has adopted
the method. Read this alongside the client's `tools/REPORTING.md` (the
client-side ritual) and SPEC §6 (the artifacts this derives from).

## What a report is in the truth stack

A report is **derived data** — the same class of thing as `GRAPH.md`. It
restates graph entities (constraints, gates, holds, seams) with their numbers
and the graph REV, alongside business content that lives nowhere else. It is
never a source of truth:

- It may cite constraints ("Constraint 2, plan-v1"); it may never restate,
  extend, or amend them (SPEC §2 load-bearing rule).
- It is regenerated from the same client commit, never hand-edited in its
  derived section. If the truth moves, the report is re-generated, not patched.
- A report without a REV is untrustworthy: the reader cannot tell which truth
  it was built from.

## What goes in every report

1. **Provenance block** — doc ref, date, author/owner, status, classification,
   and the gantry identity it was generated against: `plan <name> · REV <12> ·
   commit <8>`. This says where the content comes from.
2. **Part-of strip** — which gate, phase, decision, and file the report sits
   under (e.g. `G1 — Patents · DEC-0013 · legal/patents/`). This says what the
   content is part of.
3. **Current gantry state section** — generated by `gantry_report.py` from
   `state.json`: constraints (number, group, name), gates and phases with
   status, holds with their human-gated decision state, provisional seams with
   freeze events, open workorders with their refs, dependency edges. All
   restated, never amended.
4. **Business content** — anything the company needs to say; the template
   styles it, the report owns it.

## Citation discipline

- Cite constraints by number *and* version: "Constraint 11 (plan-v1)" — never
  a bare cardinality ("one of our 12 constraints"), never a restatement that
  could drift from the plan.
- Cite gates by slug (`g1`) and holds by slug (`Q1`, `Q2`) so a reader can
  find them in `GRAPH.md`.
- The REV shown must match the state the report was generated from; a report
  whose REV differs from the current `GRAPH.md` is a report of an older truth
  — say so in the body, don't silently update.

## The pipeline

```sh
# 1. the derived state section (deterministic; run from the gantry repo or
#    the client's tools/)
python3 scripts/gantry_report.py \
    --client <client>/.gantry/adapter.json --root <client> \
    --out <client>/tools/typst/report/state.typ \
    --title "<report title>" --author "<owner>" --date "<date>"

# 2. compile the corporate template with the business content
typst compile --root <client>/tools/typst \
    <client>/tools/typst/report/main.typ
```

The reporter reads only `state.json` + the adapter — derived over derived,
which keeps it deterministic (SPEC §6). It exits non-zero with a clear message
if `state.json` is absent (run the extractor first).

## What not to do

- Never hand-edit the generated section; it will be overwritten.
- Never put requirements in a report — requirements live in the plan; the
  report cites them.
- Never let a report become the place decisions get made silently. An open
  question in a report is a hold in the tracker or it is not an open question.
